Audit: _exhausted_attempt_terminal_transition environment-failure coverage gap via claim_task

Scope
-----
Source examined:
  src/mac/services.py  — _exhausted_attempt_terminal_transition (line 14571),
                          claim_task exhausted-attempt gate (line 7666–7672)
  src/mac/attempt_failure_classifier.py — classify_attempt_failure, _class_from_history
  tests/test_control_plane.py — all tests referencing _exhausted_attempt_terminal_transition
                                  and/or claim_task with exhausted-attempt context

Call sites of _exhausted_attempt_terminal_transition
-----------------------------------------------------
1. claim_task (line 7666) – fires when task.attempt_count >= task.max_attempts at
   claim time.  Passes detail = {"reason": "max attempts"}.
2. _expire_lease_row (line 8652) – fires when a lease expires on an already-exhausted
   task.  Passes detail = {"lease_id": ..., "agent_id": ...}.
3. _auto_retry_blocked_attempt_task (line 14764) – fires via dispatcher tick when
   attempt_count >= max_attempts on a BLOCKED task.  Passes full base_detail including
   via/backoff/ready_at.

Branch map of _exhausted_attempt_terminal_transition
-----------------------------------------------------
A. repairable_prerequisite == True  (contract_failure OR failure_class == "environment")
   A1. repair_id not yet recorded (first time)
       A1a. contract_failure → sets contract_repair_task_id, contract_repair_status="waiting",
            origin_type="contract_prerequisite"; returns (WAITING, detail with
            reason="waiting_on_contract_prerequisite", repair_task_id=...,
            manual_repair_required=False)
       A1b. failure_class == "environment" (not contract) → sets environment_repair_task_id,
            origin_type="environment_prerequisite"; returns (WAITING, detail with
            reason="waiting_on_environment_prerequisite", repair_task_id=...,
            manual_repair_required=False)
   A2. repair_id already recorded (idempotent re-entry) → skips creation, returns
       same WAITING state with matching reason key (no repair_task_id in detail)
B. failure_class == "superseded" → returns (CANCELLED, detail with reason="superseded")
C. default (failure_class == "work" / "scope") → returns (FAILED, detail)

Missing test scenarios — gaps in claim_task coverage
------------------------------------------------------
The task description asks specifically about the claim_task call site (line ~7643 in the
original; line 7666 in current HEAD).  The only existing test for that call site exercises
the contract_failure branch.  ALL environment-failure sub-paths via claim_task are untested.

FINDING 1 — claim_task + heartbeat_offline history → WAITING with environment_repair_task_id
  Title: test_claim_exhausted_attempt_heartbeat_offline_creates_environment_repair_task
  Setup:
    - Create task with max_attempts=1.
    - Transition to BLOCKED with reason="heartbeat_offline" (sets failure_class="environment"
      in the history blob used by classify_attempt_failure).
    - Manually SET state=OPEN, attempt_count=1 (simulates a re-queue after the block
      was noticed but retries are exhausted when claim is attempted).
    - Register an agent; call cp.claim_task(task.id, agent.id).
  Expected:
    - TransitionError is raised.
    - task.state == WAITING.
    - task.metadata["failure_class"] == "environment".
    - len(task.dependencies) == 1.
    - repair = cp.get_task(task.dependencies[0]);
      repair.metadata["origin"]["type"] == "environment_prerequisite".
    - task.metadata["environment_repair_task_id"] == repair.id.
    - "contract_repair_task_id" not in task.metadata.
    - "contract_repair_status" not in task.metadata.
  Why missing: test_claim_exhausted_attempt_records_failure_class uses
    verification_contract_failed; there is no parallel test for heartbeat_offline via
    claim_task.

FINDING 2 — claim_task + worker_exception history → WAITING with environment_repair_task_id
  Title: test_claim_exhausted_attempt_worker_exception_creates_environment_repair_task
  Setup:
    - Create task with max_attempts=1.
    - Transition to BLOCKED with reason="worker_exception", failure="worker_exception".
    - Manually SET state=OPEN, attempt_count=1.
    - Register an agent; call cp.claim_task(task.id, agent.id).
  Expected: same as FINDING 1 (WAITING, environment_repair_task_id, origin type, no
    contract fields).
  Why missing: worker_exception is tested via tick path but not via claim_task path.

FINDING 3 — claim_task + environment failure → transition detail contains
  reason="waiting_on_environment_prerequisite" and manual_repair_required=False
  Title: test_claim_exhausted_attempt_environment_failure_transition_detail_reason
  Setup:
    - Same as FINDING 1 (heartbeat_offline, OPEN, attempt_count=1).
    - After TransitionError, inspect cp.task_history(task.id) for the last
      event with to_state==WAITING.
  Expected:
    - event.detail["reason"] == "waiting_on_environment_prerequisite".
    - event.detail["manual_repair_required"] == False.
    - event.detail["failure_class"] == "environment".
    - event.detail["repair_task_id"] == task.metadata["environment_repair_task_id"].
  Why missing: No test at ANY call site checks the WAITING transition-history event
    detail for reason="waiting_on_environment_prerequisite", manual_repair_required=False,
    or repair_task_id presence.  The tick path test (test_tick_exhausted…detail_and_metadata)
    checks only that a WAITING event exists, not its detail fields.

FINDING 4 — claim_task + environment failure idempotency (repair_id already recorded)
  Title: test_claim_exhausted_attempt_environment_failure_idempotent
  Setup:
    - Create task with max_attempts=2.
    - Transition to BLOCKED with reason="worker_exception" (attempt 1).
    - Manually SET state=OPEN, attempt_count=2.
    - Register an agent; call cp.claim_task(task.id, agent.id) → TransitionError.
      Record repair_id = task.metadata["environment_repair_task_id"].
    - Reset state=OPEN (task already in WAITING with dependency; skip to the sub-case:
      manually inject environment_repair_task_id into metadata pre-call to simulate a
      previously recorded repair, then drive attempt_count>=max_attempts again via a
      second claim attempt, or use the method directly).
    - A cleaner approach: call _exhausted_attempt_terminal_transition directly twice
      with repair_id already present.  Or: simulate via claim_task on a task that already
      has environment_repair_task_id set and attempt_count>=max_attempts.
  Expected:
    - Second call does NOT create a second repair task.
    - task.metadata["environment_repair_task_id"] unchanged.
    - len(task.dependencies) unchanged (no duplicate dependency added).
  Why missing: idempotency is tested for the tick path
    (test_tick_exhausted_environment_repair_task_idempotent) but not for the claim_task
    call site.

FINDING 5 — claim_task + environment failure → attempt_count reset to 0
  Title: test_claim_exhausted_attempt_environment_failure_resets_attempt_count
  Setup:
    - Create task with max_attempts=1.
    - Transition to BLOCKED with reason="heartbeat_offline".
    - Manually SET state=OPEN, attempt_count=1.
    - Register agent; call cp.claim_task(task.id, agent.id) → TransitionError.
  Expected:
    - cp.get_task(task.id).attempt_count == 0.
  Why missing: attempt_count reset is tested for the tick path
    (test_tick_exhausted_environment_failure_resets_attempt_count_to_zero) but not
    for the claim_task call site.

FINDING 6 — claim_task + environment failure → contract_repair_status must not be set
  Title: test_claim_exhausted_attempt_environment_failure_no_contract_repair_status
  Setup:
    - Same as FINDING 1 (heartbeat_offline, OPEN, attempt_count=1).
  Expected:
    - "contract_repair_status" not in task.metadata.
    - "contract_repair_task_id" not in task.metadata.
  Why missing: this negative assertion is tested for tick path
    (test_tick_exhausted_environment_failure_does_not_set_contract_repair_status) but
    not for the claim_task call site.

Summary of gap
--------------
The claim_task call site of _exhausted_attempt_terminal_transition has exactly ONE test:
test_claim_exhausted_attempt_records_failure_class, which covers only the contract_failure
sub-path (verification_contract_failed history).  The environment-failure sub-path
(triggered by heartbeat_offline or worker_exception history) is not exercised via
claim_task in any test.

Six concrete missing scenarios:
  1. heartbeat_offline → WAITING + environment_repair_task_id via claim_task
  2. worker_exception → WAITING + environment_repair_task_id via claim_task
  3. transition-detail fields (reason, manual_repair_required, repair_task_id) via claim_task
  4. repair-task idempotency (environment_repair_task_id already present) via claim_task
  5. attempt_count reset to 0 via claim_task
  6. absence of contract fields on environment path via claim_task

All six scenarios have direct analogues in the tick-path tests; the repair task
implementation can use those as templates and change the invocation from
"cp.tick(limit=0) on a BLOCKED task" to
"cp.claim_task(task.id, agent.id) on an OPEN task with attempt_count >= max_attempts".
