# Agent output truncation silently produces no work on large single-turn generations

## Why this exists

In the taskbrain build, task F7 (scaffold the Typer CLI) failed **deterministically,
6+ times, on both the hub and a worker, even with explicit hints** — yet it's a
task Claude Sonnet 4.6 is trivially capable of. The executor evidence is the tell:
`returncode: 0`, `result: "Response truncated due to output length limit"`, and
**zero files written** → the deterministic finalizer sees a clean tree → "repo
evidence requires changed files".

Mechanism: the agent's single LLM turn hits the model's **max-output-tokens cap**
(`finish_reason=length`); the Hermes conversation loop records the truncation
(`src/mac/_hermes/agent/conversation_loop.py:1764,1781,1794`) and the turn ends
**mid tool-call**, so the `write_file` never completes. The "first response
truncated - cannot recover" path (~:1794) just marks the run failed. This is an
**output-budget + truncation-handling defect, not a capability wall**, and it
correlates with single-turn output size: tasks that build incrementally (F9, M2-7)
stay under the cap and converge; "generate a large new module in one shot" (F7)
truncates every time.

It mattered badly: F7 gated M1-6 + M1-7, and M1-7 cascaded through M1-12 → M2-1 →
essentially all of M2/M3 — i.e. one truncation defect stalled ~26 of the remaining
tasks.

Compounding factor: a **structural ambiguity** — pyproject's entry point is
`taskbrain.cli:app` and `taskbrain/cli.py` already exists, but F7's task says
`apps/cli/main.py` — so the agent also spends output budget deciding *where* the
CLI goes, making truncation more likely.

## Shipped (fix #1)

The in-mac router now **floors chat-completion `max_tokens`** before forwarding
(`src/mac/router_app.py` `_ensure_max_tokens_floor`, applied in `_route`):
`MAC_ROUTER_MAX_TOKENS_FLOOR` (default 32000; 0 disables). `max_tokens` is a cap
not a target, so short completions still stop at `finish_reason=stop`; embeddings
untouched. Deployed to the hub (where the inproc router runs). Test:
`tests/test_router_app.py::test_max_tokens_floor_rescues_large_chat_generations`.

## Remaining follow-ups (robustness — the durable fix)

1. **Auto-continue on `finish_reason=length`** in the Hermes conversation loop
   (`_hermes/agent/conversation_loop.py:1764+`): instead of failing the turn,
   re-prompt the model to continue/finish the output (or re-issue the tool call),
   so large generations complete regardless of any cap — including the current
   "first response truncated - cannot recover" dead end.
2. **Classify truncation as a distinct, retryable failure** in the executor
   (`task_executor.classify_outcome` / the finalizer): detect "truncated + zero
   changed files" and record an *actionable* `deployment_learning` ("prior attempt
   truncated — write the file in smaller chunks") + requeue with that hint, rather
   than the useless generic "no changed files". (Ties to [[gate-testdeps-01]] /
   the learning-quality theme.)
3. **Prompt for incremental writes** in `task_executor.build_task_prompt`: write
   large files via multiple smaller edits, not one giant response.
4. **Remove the structural ambiguity**: pin one canonical CLI layout
   (`taskbrain/cli.py` per the entry point) and have onboarding author tasks
   consistently with the repo's real layout.

## Verification

- Re-run F7 with the router floor in place: the agent should complete the CLI
  generation and write files (no "Response truncated"), the gate passes, and F7
  merges — unblocking the M1-6/M1-7 → M1-12 → M2-1 cascade. (In progress.)
- Longer term, with fix #2, induce a truncation (tiny `MAC_ROUTER_MAX_TOKENS_FLOOR`)
  and confirm the agent auto-continues to completion instead of failing.
