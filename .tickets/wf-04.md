# Planner node type (description → plan → parameterize downstream nodes)

**Problem.** Drafts have a `description → proposed_steps` shape but no execution-time planner. A user who knows what they want ("build me a feature that does X") still has to author `proposed_steps` themselves; the workflow takes over only after that. There's no first-class "planner" step that an agent can run.

## Acceptance Criteria

- New `node_type="plan"`: when the runtime advances to a plan node, it spawns a task whose role is "translate the workflow's input description into the parameters of downstream nodes." The task's evidence carries a structured `plan` artifact: `{ "node_payloads": { "<node_key>": { "instructions": "...", "metadata": {...} } } }`.
- After a plan node completes, `_advance()` injects each `node_payload` into the matching downstream node BEFORE that node spawns its task. Nodes without an entry in the plan use their static definition unchanged.
- New built-in template: `data/workflows/feature_from_description.json` — a worked example where node 1 is `node_type="plan"`, node 2 onward are the regular feature workflow nodes parameterized by the plan.
- The free-form initial description is supplied as a `start_workflow` body field (`description: str`); the runtime exposes it to the plan node as task metadata.
- Test: start the new template with a description like "add Slack DM support to the notifier"; assert the plan node runs, emits a plan, and the downstream `pm_approve` node's instructions contain the resolved values.

Blocked by [wf-01](wf-01.md) (the plan payload may itself need question/answer wiring). Independent of [wf-02](wf-02.md), [wf-03](wf-03.md).
