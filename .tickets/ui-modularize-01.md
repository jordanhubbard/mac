# Split the monolithic dashboard `app.ts` into per-view modules

## Why this exists

The dashboard control-plane UI lives in a single hand-maintained TypeScript
file that has grown to **8,434 lines** (`src/mac/ui/app.ts`), with its compiled
sibling `src/mac/ui/app.js` at 7,687 lines and `src/mac/ui/styles.css` at 2,750
lines. One file holds the render functions for all 14 views (Overview, Work,
Projects, Tasks, Workflows, Map, Fleets, Agents, Hermes, Operations,
Integrations, Runtime, Observability, Secrets) plus connection/auth bootstrap,
global state, the AgentBus terminal, and the Hermes config-apply editor.

This is the dominant maintainability liability in the UI:

- **Hard to navigate / review** — every feature change touches the same giant
  file, making it a merge-conflict magnet across the parallel agent workflows
  that produce most UI commits.
- **Untestable in isolation** — render functions can't be unit-tested; the only
  coverage today is the integration-style shell test
  (`tests/ui/test_ui_shell.py`, ~421 lines) that asserts on emitted HTML/CSS.
- **Dual-source drift risk** — the compiled `app.js` is checked in next to
  `app.ts` and regenerated by a manual `tsc` step
  (`cd src/mac/ui && npx -y -p typescript@5 tsc ... && cp /tmp/uib/app.js app.js`).
  Nothing enforces that the committed `.js` matches the `.ts`.

## Design

Keep the zero-bundler, static-asset serving model intact (no webpack/vite, no
npm in the serving path — this is a genuine strength worth preserving). The
goal is modular *source*, not a new build pipeline.

1. Split `app.ts` into ES modules under `src/mac/ui/` — e.g.
   `state.ts`, `connection.ts` (the `?t=`/`?api=` bootstrap + sessionStorage),
   `api/` (the `dashboard_api.ts` layer), `terminal.ts` (xterm + AgentBus),
   and one module per view under `views/` (`views/hermes.ts`, `views/tasks.ts`,
   …). `app.ts` becomes a thin router/bootstrap that imports them.
2. Emit a single `app.js` from `tsc` using `--module es2020` (already the flag
   in use) so the browser loads one ES module entrypoint; confirm
   `src/mac/api.py` static mount (`/ui/assets`, ~`api.py:2728`) serves any
   additional emitted files.
3. Add a **CI check that the committed `app.js` is byte-identical to a fresh
   `tsc` build** so source/compiled drift can't land silently (closes the gap
   noted above). Wire it into `scripts/run-contract-tests.sh`.
4. Consider splitting `styles.css` per-view as a follow-on (lower priority).

## Acceptance Criteria

- `src/mac/ui/app.ts` is reduced to a bootstrap/router; no single UI source
  file exceeds ~1,500 lines.
- `tests/ui/test_ui_shell.py` still passes; the served `/ui` is functionally
  unchanged (all 14 views render, terminal + Hermes apply still work).
- CI fails if `app.js` is not the exact output of compiling the `.ts` sources.
